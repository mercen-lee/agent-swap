## beta.13 재로그인 뒤 반복 Keychain 승인

선택 계정의 재로그인 작업이 interactive TaskLocal을 상속한 채 후속 사용량 조회까지 실행했습니다. Claude 조회는 다른 저장 계정의 소유자 증명도 읽으므로, 한 계정의 재로그인 뒤 다른 항목의 승인 창이 이어질 수 있었습니다. 후속 조회만 noninteractive로 전환하고 선택한 새 인증의 저장·재읽기 권한은 유지했습니다.

수정 전 Claude·Codex 두 경우에서 실패하는 회귀를 확인했고, 수정 후 관련 **12개 테스트·1개 스위트**, 전체 Core **493개 테스트·48개 스위트**가 통과했습니다. Release 앱 빌드·deep/strict 서명과 diff 검사도 통과했습니다. 선택 계정의 저장 검증 이후 모든 vault 읽기·사용량 조회가 noninteractive이며 다른 Claude 소유자 증명을 계속 복원하고 인증 적용·회전을 하지 않는지 확인했습니다. 실제 계정의 재로그인을 테스트 fixture로 대체하지 않습니다.

별도의 beta.12 실계정 복구에서는 저장 인증의 만료와 사용량 HTTP 401을 확인했습니다. 공식 CLI의 모델 요청 없는 `/usage` 실행 뒤 현재 네이티브 인증의 프로필 확인이 성공했습니다. 사용자가 요청한 수동 재확인을 위해 과거 429의 예약 메타데이터만 백업 후 해제했으며, 이것을 서버 제한 자체가 해제됐다는 증거로 해석하지 않습니다. 사용자 승인과 재로그인 처리 후 설치된 앱에서 등록된 모든 계정의 새 사용량 조회 성공과 오류·재시도 대기 해제를 확인했습니다. 실제 사용량·식별자·인증은 문서에 포함하지 않습니다. 기존 Desktop 관련 프로세스 17개의 PID·시작 시각·실행 파일이 모두 유지됐고 Desktop 종료·계정 전환은 실행하지 않았습니다.

beta.12 복구 시점에는 앱 서명과 저장 항목의 ACL·partition이 일치하는 메타데이터도 확인했습니다. 오류 `-25293`만으로 승인이 누락됐다고 판단하지 않습니다. 격리된 합성 Keychain에서 LAContext 유무는 잠금·해제 상태별 결과에 차이가 없었으므로 인증 context를 제거하지 않았습니다.

beta.13의 CI와 Universal 패키징이 성공했고 공개 ZIP·피드·체크섬, 두 아키텍처의 여섯 Mach-O·macOS 14·beta.12의 DR와 업데이트 공개키 연속성을 확인한 뒤 릴리즈를 공개했습니다. Sparkle 설치·재실행 뒤 설치 파일·심볼릭 링크 71개가 서명된 ZIP과 일치했습니다. 기존 Desktop 관련 프로세스 17개의 PID·시작 시각·실행 파일도 유지됐습니다.

사용자의 화면 잠금 해제 후 AgentSwap만 정상 종료하고, 승인됐던 beta.12의 검증된 공개 앱으로 설치본을 되돌렸습니다. 교체 전 단일 실행 잠금과 프로세스 부재를 확인하고 beta.13 앱은 로컬에 보관했습니다. 앱 교체 과정에서 인증·상태 파일을 이전 사본으로 복원하지 않았습니다. 다시 실행한 beta.12의 전체 새로고침에서 Claude 다섯 계정과 Codex 한 계정 모두 2분 이내의 새 정상 응답, `UsageCache.error`·재시도 대기 부재를 확인했습니다. 추가 승인 창은 관찰되지 않았고 기존 Desktop 관련 프로세스 17개의 PID·시작 시각·실행 파일도 모두 유지됐습니다. 현재 설치본은 beta.12이며 beta.13의 배포 서명 문제가 해결된 것으로 표시하지 않습니다.

## beta.12 다음날 조회 실패와 서버 제한

Claude 토큰 갱신 성공 후 새 토큰을 먼저 저장하고 별도 프로필 요청으로 binding을 만들던 경로를 수정했습니다. 후속 프로필 요청이 제한되거나 실패하면 새 토큰이 소유자 증명 없이 저장될 수 있었고, 재시작 후 그 토큰까지 만료되면 유효한 갱신 토큰이 남아도 계정 확인 단계에서 갱신이 막혔습니다. 이제 검증된 정확한 grant의 고정 OAuth endpoint 갱신 성공 응답에 새 토큰 쌍의 binding을 붙인 뒤 첫 영구 저장·복구 marker를 만듭니다. 처음 보는 토큰·캐시·다른 계정의 인증을 신뢰하는 우회는 추가하지 않습니다.

HTTP 429는 같은 제공자 전체의 다음 요청을 보류하고 서버가 정한 가장 늦은 시각을 상태에 저장합니다. 기존 계정별 서버 대기도 시작 시 합칩니다. 다른 계정·동시 새로고침·앱 재시작·접근 승인·전환으로 우회하지 않으며 다른 제공자의 조회는 계속됩니다. 화면에는 조회 실패 대신 서버 조회 제한과 재시도 시각을 표시합니다. 합성 상태의 `--demo --demo-rate-limited --demo-narrow`로 확인할 수 있습니다.

참고한 [claude-profile-manager](https://github.com/JakubKontra/claude-profile-manager/tree/75182c80fabf6e2ab31295ab7d1d6faa2bd38087)는 프로필별 `CLAUDE_CONFIG_DIR`와 Keychain 서비스를 분리하고 공식 CLI가 각 저장소의 최신 인증을 관리합니다. 자체 OAuth 조회·갱신 구현이 아니므로 AgentSwap의 공유 네이티브 인증·vault 동기화가 같은 유지 특성을 갖는다고 판단하지 않습니다.

새 회귀 **21개 테스트·3개 스위트**, 전체 Core **492개 테스트·48개 스위트**가 통과했고 Release 앱 빌드와 diff 검사도 통과했습니다. 첫 vault·복구 marker의 binding, 후속 사용량 429·재시작·재만료·재갱신, 첫 저장 실패 후 OAuth 무재교환 재시도, 잘못된 계정의 증명 거부, 정확한 네이티브 토큰 쌍의 401 중복 억제를 확인했습니다. 제공자별 일괄 요청 중단·다른 제공자 진행·동시 새로고침·최장 대기 복원·구버전 상태·접근 승인과 로그인·전환의 대기 유지도 확인했습니다. 합성 Desktop spy에서 제한 중 캡처·종료 준비·적용이 0회임을 확인했고, 새 로그인과 전환 대상 프로필의 첫 429도 영구 대기로 이어집니다. 최소 크기 메모리 데모에서 계정 목록·상세의 안내와 재시도 시각을 확인했습니다.

계정은 드래그와 툴바·우클릭 메뉴의 위·아래 이동으로 정렬할 수 있습니다. 대시보드와 메뉴바가 같은 표시 순서를 사용하고, 제공자 필터·검색에 숨겨진 계정의 위치와 원래 등록 순서·자동 전환 동률 기준은 유지합니다. 구버전 상태의 새 선택적 필드 부재, 중복·삭제된 ID, 새 계정, 잘못된 이동과 오래된 화면 스냅샷도 확인했습니다.

관련 **25개 테스트·3개 스위트**, 전체 Core **471개 테스트·45개 스위트**가 통과했고 Release 앱 빌드와 diff 검사도 통과했습니다. 재로그인 대상 불일치·취소·저장 순서·읽기 검증 실패·재시작·명시적 적용과 가져오기·종료 시 재시도, 필터 이동·순서 재로드·자동 전환 기준 불변을 합성 fixture로 확인했습니다. 실제 Claude 어댑터의 독립 갱신 fixture에서는 잠금 안의 다른 소유자 확인, 동일 소유자로 바뀌는 경쟁의 OAuth 이전 거부, 첫 저장 실패 후 무재교환 재시도와 네이티브 불변을 확인했습니다. 메모리 데모의 재로그인 시트에서 대상 정보·안내·취소와 줄바꿈을 확인하고, 툴바 메뉴로 목록 순서를 바꾼 뒤 선택이 유지되는지 확인했습니다. 실제 계정의 재로그인·계정 전환·Desktop 종료는 실행하지 않았습니다.

## beta.10 현재 Claude 로그인 확인과 저장 계정 조회의 분리

- beta.5 통합 전 작업본에서 고유 scratch 경로를 지정한 전체 Core **327개 테스트·31개 스위트**, Release 앱 빌드와 plist·diff 검사를 통과했습니다. 이는 beta.5 기능을 합친 최종 릴리즈 테스트 개수가 아닙니다. 기존 Keychain deprecation 경고는 남아 있습니다.
- 통합 전 메모리 데모에서 Desktop 화면·프로필 추가·합성 프로필 열기·마지막으로 연 프로필 표시를 확인했습니다. 760×520pt에서 안내문 줄바꿈과 목록·고정 상태바를 확인했습니다. 창 복원 크기가 `--demo-narrow`를 무시하던 동작도 데모 모드에 한정해 수정했습니다. 본 작업에서는 실제 사용자 인증·Desktop 종료·실계정 계정 전환을 실행하지 않았으며, 실행 중인 Desktop·Code 세션을 유지하라는 사용자 요청을 유지합니다.

**남은 검증:** 3.1623.0 독립 프로필의 최초 브라우저 로그인·콜백, 서로 다른 두 계정의 Code 탭 실제 요청과 원래 프로필 복귀, 1시간 이상 로그인 유지. 새 프로필에서 기존 Code 대화의 계정 간 이어쓰기는 보장하지 않습니다. Claude in Chrome의 로컬 pairing은 데이터 폴더 변경 시 제한되며 일부 CLI 설정·transcript는 여전히 공용 `~/.claude`를 사용할 수 있으므로 전체 파일 격리로 표시하지 않습니다. 자동 전환과 사용량 조회는 기존 CLI·Codex 계정 기능이며 새 독립 Desktop 프로필과 자동 연결하지 않습니다. 아래 beta.5 및 2.42304.0의 실계정 검증은 당시 구현·설치 버전의 기록이며 이번 작업에서 재수행한 것으로 해석하지 않습니다.

## beta.6 업데이트 검증 범위

앱 업데이트는 Sparkle 2.10.0과 GitHub Release의 버전별 `appcast.xml`·EdDSA 서명 ZIP을 사용합니다. 자동 확인 기본 주기는 24시간이며 자동 다운로드·설치는 기본 꺼짐입니다. 베타 설치본과 정식 설치본의 릴리스 선택 범위를 구분하고, draft·불완전한 첨부 파일은 제외합니다. beta.5 이하 설치본에는 업데이트 기능이 없으므로 beta.6의 최초 설치는 수동입니다.

beta.5 통합 및 이전 복구 저널의 Desktop 실행 차단을 포함한 전체 Core **409개 테스트·38개 스위트**가 3.209초에 통과했습니다. 업데이트 후보 선택은 숫자형 prerelease 정렬, 정식·베타 채널, 초안·자료 누락·외부 URL·잘못된 버전·응답 크기 제한을 합성 자료로 확인했습니다. 앱 종료와 대기 중인 Desktop 프로필 작업·CLI 로그인 취소가 공유 큐에서 교착되지 않는 통합 fixture도 포함합니다. 과거 복구 저널이 남으면 기본 Desktop·독립 프로필 모두 디렉터리 준비·프로세스 조회·종료·실행 전에 거부하며, 저널이 없으면 두 실행 경로가 허용되는 fixture를 추가했습니다.

격리된 `0.1.0-beta.6-verify` 패키징에서 ZIP 복원 후 앱·Sparkle·Autoupdate·Updater·Downloader·Installer의 Universal arm64/x86_64 및 개별 서명, 앱의 최소 macOS 14·Hardened Runtime·디버깅 entitlement 부재와 deep·strict 서명을 확인했습니다. 공개용 ad-hoc 앱에는 별도 서명 Sparkle을 불러오기 위한 library validation 예외를 적용합니다. 피드 서명·체크섬과 번들 공개 키에 대한 ZIP의 Ed25519 서명을 확인했고, 합성 자료의 ZIP 변조·잘못된 공개 키를 거부했습니다. 이 검증용 버전은 공개하지 않았습니다.

실제 다음 버전으로의 다운로드·설치·재실행과 Keychain 접근 유지 검증은 별도 증거가 필요합니다. 업데이트 서명·패키징 검증이 완료되어도 Developer ID 서명·Apple 공증이나 실계정 전환 검증으로 표시하지 않습니다. 실행 중인 사용자 Desktop·Code 세션을 종료하는 업데이트 검증은 수행하지 않습니다.

새 브랜드 자산은 Claude의 Simple Icons 원본·색상과 공식 OpenAI SVG를 고정해 포함했습니다. 앱 아이콘 PNG 10개의 크기·투명도와 SVG 원본 무결성·외부 참조 부재를 확인했습니다. Release 앱의 760×520pt 메모리 데모에서 밝은·어두운 모드의 사이드바·계정 행·상세 아이콘과 업데이트 설정을 확인했습니다. 밝은 모드의 회색 선택 행에서도 텍스트와 같은 의미 기반 전경색을 사용합니다. 출처·라이선스·생성 프롬프트는 [브랜드 자산 안내](BRAND_ASSETS.md)에 기록했습니다.

## 재현 명령

전체 Xcode를 사용합니다. Command Line Tools만 선택된 환경에서는 Swift Testing 모듈이 없을 수 있습니다. 현재 앱 Release 빌드는 Xcode 27과 macOS SDK 27로 검증합니다.

```sh
./scripts/test-core.sh
./scripts/test-core.sh --filter AutomaticSwitchTests
./scripts/build-app.sh
codesign --verify --deep --strict build/AgentSwap.app
plutil -lint AgentSwapApp/Info.plist AgentSwap.xcodeproj/project.pbxproj
```

테스트 스크립트는 Xcode의 `xcrun swift`, native SwiftPM, 별도 scratch 경로를 사용합니다. 기본 캐시는 `build/CoreTests`이며 동시 실행 시 `AGENTSWAP_TEST_SCRATCH_PATH`를 서로 다르게 지정합니다. 실행 중인 앱을 빌드 스크립트로 덮어쓰지 않습니다.

## 자동 검증

초기 베타 검증에서 Core **252개 테스트·20개 스위트 통과**, Release **BUILD SUCCEEDED**, 앱 deep·strict 서명 검증과 plist·diff 검사 통과를 확인했습니다. 기존 macOS Keychain API의 deprecation 경고는 남아 있으며, 확인한 빌드에는 동시성 경고나 컴파일 오류가 없었습니다.

저장소 준비 과정에서도 새 `scripts/test-core.sh`로 252개·20개 스위트가 통과했습니다. 전용 skill·CI YAML·내부 문서 링크·shell 문법·ignore 규칙과 index의 비밀 정보 후보 검사를 통과했습니다. 기본 앱을 교체하거나 인증을 변경하지 않았습니다.

첫 GitHub CI는 Core 빌드를 완료했지만 테스트 실행이 끝나지 않고 작업의 20분 제한 부근에서 취소됐습니다. 별도 strict cooperative pool 실행에서 Codex 취소 fixture의 동기 대기로 테스트가 정체되는 문제를 재현했습니다. 취소·해제 제어를 독립 Dispatch 실행기로 옮기고 대기에 상한과 실패 assertion을 추가했으며 기존 병렬화·인증 보존 검증은 유지했습니다. 수정 후 관련 9개 테스트가 strict·일반 실행 모두 통과했고, 전체 252개·20개 스위트도 일반 2.973초·strict 3.502초에 통과했습니다. 이 로컬 재현을 첫 원격 실행의 유일한 원인으로 단정하지 않으며 수정본의 원격 CI에서 Core 테스트 통과를 확인했습니다. 이어진 앱 Release 빌드는 Xcode 26.6·Swift 6.3.3의 컴파일러 내부 IR 생성 중 충돌했습니다. 따라서 CI와 릴리즈 workflow를 로컬 Universal 빌드가 통과한 Xcode 27 도구로 맞췄으며, macOS 실행 최소 버전 14.0은 유지합니다. 다른 앱 빌드 도구의 호환성은 확인하지 않았습니다.

Fixture는 합성 인증, 임시 디렉터리, 주입한 HTTP·Keychain·프로세스 제어를 사용합니다. 테스트를 실행하기 위해 실제 계정에 로그인할 필요는 없습니다.

`scripts/package-release.sh`로 격리된 Universal Release 빌드와 개발용 ZIP·SHA256SUMS 생성을 확인했습니다. ZIP을 다시 추출한 앱의 deep·strict 서명, arm64·x86_64 아키텍처, `net.mercen.agentswap` 번들 ID, 요청한 버전·빌드 번호, 최소 macOS 14.0, 체크섬이 모두 일치했습니다. 실행 중인 기본 앱의 실행 파일 바이트도 기존과 같았습니다. 실제 앱 실행이나 계정 인증 변경은 수행하지 않았습니다.

버전별 출력 폴더의 기존 산출물을 덮어쓰지 않습니다. GitHub의 버전 태그 workflow는 테스트·패키징·검증 후 초안 prerelease를 만듭니다. `v0.1.0-beta.1`은 이 workflow에서 만든 ZIP·체크섬을 다시 내려받아 검증하고 공개 prerelease로 발행했습니다. ad-hoc 개발용 ZIP을 제공하는 경로이며 Developer ID 서명·공증·DMG와 실제 계정 검증은 별도 완료 조건입니다.

## beta.2 인증·전환 수정 검증

첫 베타의 Claude 인증 크기 제한은 현재 A의 원본을 복원할 수 없게 하므로 B 전환까지 보류했습니다. 큰 인증 경로를 추가하면서 모든 before/after 사전 검증과 정확한 복원 조건을 유지했습니다.

- private 임시 Keychain의 합성 자료 약 64 KiB에서 큰 기존 항목 갱신·작은 원본 복원·없는 항목의 원자 생성 후 별도 SecurityTool의 2초 읽기가 정확한 바이트와 일치했습니다. Swift interpreter를 신뢰 앱에 명시하지 않은 SecurityTool 기본 ACL에서도 기존 항목 갱신·복원이 통과했습니다. helper 자체 읽기 성공은 근거로 사용하지 않습니다.
- 번들 resource 코드의 실제 Security 호출도 임시 Keychain에 한정하는 search list·use keychain scope 두 곳만 실험용으로 주입해 같은 결과를 확인했습니다. 사용자의 default/search list·실제 인증은 변경하지 않았고 모든 실험 Keychain과 소유한 임시 디렉터리를 정리했습니다.
- 큰 before/after·공유 MCP/플러그인 값, 부분 실패·취소 후 복원, CLI 출력 한도와 표준 입력 전송 경계, 도구 부재·잘못된 외부 읽기·변조된 resource 거부를 fixture로 확인했습니다.
- 권한 상태가 바뀐 뒤 호환성 갱신과 다른 정상 계정의 전환, 조회 실패 시 마지막 정상 값·인증 상태 보존, 읽기 전용 명시 재확인, 저장 오류의 전환 안내를 fixture로 확인했습니다.

## 이 Mac의 Claude 전환 차단 수정

Claude 데스크톱 2.37337.1의 등록된 로컬 목록을 읽기 전용으로 확인해 정상 메타데이터 누락, 비활성 `steeredByRemoteClient: false` 거부, 선택 필드 `promptAppendSnapshot.toolSets`의 필수 처리가 순서대로 전환을 차단하는 것을 확인했습니다. 설치 serializer·reader와 실행 코드에서 자료형을 대조했으며 기준 chunk의 SHA-256은 기존 조사와 같은 `b478390bb54cc60483eed713a8ed913bb53def6c0f4b72fee381ff64436666a9`입니다. 실제 필드 값이나 대화 내용은 fixture와 문서에 복사하지 않았습니다.

- 확인된 요약 표시 플래그와 브랜치 목록은 보존합니다. MCP 도구·서버 설정, 세션 실행 설정, 오류·이전 실행·요약 상태는 자료형을 검사하되 새 대상 목록에는 전달하지 않습니다. 원본과 기존 대상은 바이트 단위로 유지합니다.
- 중단·원격 제어 marker는 `null`과 `false`만 허용하고 `true`·잘못된 자료형은 계속 차단합니다. 선택적인 `toolSets` 누락과 빈 객체는 원형 그대로 보존합니다.
- 합성 회귀 테스트로 정상 형식, 기존 대상 보존, 새 대상의 설정 초기화, 잘못된 자료형의 프로세스 검사·종료·쓰기 전 거부를 확인했습니다. 관련 스위트 **50개**, 전체 Core **301개 테스트·25개 스위트**가 통과했습니다.
- 실제 등록된 목록 **2개 모두** 수정한 parser의 읽기 전용 검사를 통과했습니다. 이는 인증 적용이나 두 계정 전환 성공 증거와 구분합니다.
- 실제 목록 준비 경로는 파일 쓰기·프로세스 종료를 거부하는 주입 경계로 확인했으며, 전체 inventory를 통과한 뒤 쓰기 전의 의도한 중단점에 도달했습니다. Universal Release 앱 빌드와 deep/strict 서명 검사가 통과했고 설치된 앱을 교체해 정상 실행을 확인했습니다.

사용자가 macOS Keychain 접근을 승인한 뒤 이 Mac의 서로 다른 Claude 계정 A → B 전환이 완료됐습니다. 공식 `claude auth status --json`의 로그인·구독 인증 상태와 대상 이메일·조직 일치를 확인했습니다. 기존 목록 원본의 바이트는 유지됐고 새 대상 목록 2개는 실행·MCP 설정을 초기화한 상태로 준비됐으며 보존 저널도 정리됐습니다. B → A 복귀는 이번 확인에 포함하지 않았습니다.

이후 Claude 데스크톱의 공식 로그아웃·Google 로그인 절차에서 사용자가 직접 인증을 완료했습니다. 데스크톱 프로필 메뉴의 대상 이메일 일치, 기존 로컬 Code 대화 2개의 목록 표시와 기존 대화 화면을 확인했습니다. 해당 화면에는 사용자의 재시도와 새 응답도 표시됐습니다. 이는 사용자의 별도 데스크톱 로그인과 함께 확인한 결과이며 AgentSwap이 데스크톱 로그인을 자동 전환한 증거가 아닙니다. 계정 소유 Remote Control 연결의 이전은 확인하지 않았습니다.

원격 연결 이력은 계정별 바인딩으로 확인돼 신규 대상에서는 제외하고 기존 대상의 값·순서·필드 부재를 보존하도록 보강했습니다. 잘못된 배열 형식과 변환 후 파일 크기 초과는 거부합니다. 이미 관찰한 하위 프로세스가 고아가 된 뒤에도 같은 PID·시작 시각이면 재시도에서 계속 추적하며, 종료·PID 재사용·확인 불가를 구분합니다. 이 Mac의 종료된 좀비 PID가 `kill(pid, 0)`에는 남지만 두 libproc 조회에는 `ESRCH`인 상태도 확인했습니다. libproc의 `ESRCH`만으로는 종료를 추정하지 않습니다. `kill(pid, 0)`의 `ESRCH` 또는 성공·정확한 크기의 `KERN_PROC_PID` 결과가 `SZOMB`인 경우만 종료로 인정합니다. 다른 조회 실패는 계속 중단합니다. 합성 프로세스 상태 및 실제 호스트의 종료 판정 회귀를 포함해 전체 Core **366개 테스트·31개 스위트**가 3.186초에 통과했습니다.

개발용 ad-hoc 서명의 콘텐츠 해시 기반 식별은 재빌드마다 AgentSwap 자체 Keychain vault의 재승인을 일으킬 수 있었습니다. 이 Mac의 기존 Apple Development 인증서로 설치본을 서명했고, 로컬 서명 선택 파일은 Git에서 제외했습니다. 빌드 스크립트는 ad-hoc Xcode 산출물을 선택한 인증서로 다시 서명합니다. 실제 기본 스크립트 빌드·서명 검증과, 콘텐츠를 바꾼 두 앱의 코드 해시는 달라도 designated requirement가 같은 것을 확인했습니다. 인증서·개인키·개발자 식별자는 문서나 저장소에 넣지 않았습니다. 임시 서명에서 안정 서명으로 이동한 첫 항목별 승인은 별도로 필요합니다. 이후 같은 설치본으로 재빌드한 뒤 AgentSwap 자체 vault의 항목별 재승인은 다시 나타나지 않았고, 실제 Safe Storage·계정별 저장 인증의 승인을 마친 뒤 등록된 세 계정의 조회 오류가 모두 해제되고 정상 값이 갱신됐습니다. 같은 설치본의 Desktop 로그인 재저장은 추가 비밀번호 요청 없이 완료됐습니다. 다만 실제 Claude 결합 전환의 한 방향에서 SecurityAgent 실행과 전환 대기 상태가 관찰됐습니다. 표시된 요청 앱·Keychain 항목과 사용자 처리 여부를 기록하지 못했으므로 추가 승인 여부나 원인은 확정하지 않았습니다. 코드상 작은 인증은 `/usr/bin/security`, 큰 인증은 Apple Swift interpreter를 쓰므로 두 실행 경로의 ACL 차이는 가능한 설명일 뿐 실제 진단은 아닙니다.

## beta.5 릴리즈 검증 (2026-10-19)

릴리즈 리뷰에서 파일에만 Claude 인증이 있던 프로필의 갱신 중단 저널이 현재 로그인 보존 복구에서 거부되는 누락을 수정했습니다. Keychain-only·Keychain+file·file-only의 정확한 위치별 원본 상태만 허용하며, 잘못된 부재 상태는 계속 거부합니다. 실제 파일 쓰기·Keychain 복원 실패로 만든 저널에서 제3세대 현재 인증을 보존하는 회귀를 추가했습니다.

최종 전체 Core **368개 테스트·31개 스위트**가 3.259초에 통과했습니다. `AGENTSWAP_SIGN_IDENTITY=- ./scripts/build-app.sh`의 Release 빌드와 deep·strict 서명 검증, 프로젝트·Info.plist 검사 및 셸 문법 검사를 통과했습니다. 릴리즈 준비 과정에서는 실제 계정 인증이나 Desktop 대화를 변경하지 않았으며 위의 실계정 검증을 새로 수행한 것으로 표시하지 않습니다.

## 호환성 제한

Claude의 네이티브 Keychain은 Apple `/usr/bin/security`의 고정 인자와 hex stdin 경로를 사용합니다. SDK 저장 후 자체 읽기와 API 조회만 성공하고 CLI 읽기는 실패한 이전 경로와 구분합니다. 네이티브 경로의 실제 CLI 왕복 성공은 설치 버전과 지원 입력 크기에 한정합니다.

- 작은 인증의 SecurityTool 명령 한도는 4094바이트입니다. 큰 인증은 Apple Swift interpreter 경로로 처리하며, CLI 읽기 출력 한도에 따라 ASCII 999,999바이트·비출력 바이트가 있는 기존 자료 499,999바이트까지 지원합니다. 전송 자체에는 추가 1 MiB 상한이 있습니다. Apple Command Line Tools 또는 Xcode·SDK가 없거나 도구 서명·resource digest 검증이 실패하면 쓰기를 중단합니다. 이를 사용자의 로그인 오류로 표시하지 않습니다.
- 값 없는 `-w`의 비밀번호 입력은 공개 소스에서 `getpass()`의 128바이트 버퍼를 사용합니다. 큰 인증을 전달하는 대안으로 사용하지 않습니다. [SecurityTool](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/keychain_add.c), [Libc](https://github.com/apple-oss-distributions/Libc/blob/main/gen/FreeBSD/readpassphrase.c), [버퍼 정의](https://github.com/apple-oss-distributions/Libinfo/blob/main/lookup.subproj/pwd.h)
- 앱 vault·복구·Codex의 Swift Security 호출은 백그라운드 승인 UI를 금지합니다. 별도 Claude SecurityTool에는 이 정책이 상속되지 않습니다. 잠금 사전 확인과 2초 제한을 적용하지만 승인 창이 절대 나타나지 않는다고 보장하지 않습니다.
- 개발 빌드는 기본 ad-hoc 서명입니다. 재빌드로 코드 식별값이 바뀌면 Keychain의 기존 `항상 허용`과 별도로 항목별 승인을 다시 요청할 수 있습니다. 같은 개발 인증서를 반복해 쓰는 이 Mac에서는 공개 인증서 SHA-1만 담은 로컬 `.agentswap-signing-identity`를 사용해 이 변경을 피할 수 있습니다. 환경 변수 `AGENTSWAP_SIGN_IDENTITY=-`는 언제나 ad-hoc을 명시합니다.
- 검증된 갱신 응답의 첫 영구 저장 이전에 강제 종료·시스템 중단이 발생하면 RAM에만 있는 새 인증은 복구할 수 없습니다. 정상 종료 대기와 첫 저장 이후 복구는 fixture로 검증했습니다.
- 기본 로컬 구독 프로필이 대상입니다. API 키, 프로젝트별 실행, 클라우드 동기화, 인증 내보내기, 관리 정책·별도 secrets 백엔드는 v1 범위에 포함하지 않습니다.
