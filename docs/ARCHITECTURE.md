# 구조와 안전 조건

## 모듈과 상태

Xcode 앱 타깃은 SwiftUI·AppKit을 담당하고 로컬 Swift Package `AgentSwapCore`는 모델·계정 관리·저장소·제공자 어댑터를 담당합니다. Swift 언어 모드는 6이며 엔진은 기본 비격리, UI 관찰 상태는 `@MainActor`입니다.

`WindowGroup`, `MenuBarExtra(.window)`, `Settings`는 동일한 `@Observable AppModel`을 받습니다. `start()`는 중복 호출을 막으며 앱 수명의 단일 조회 작업을 시작합니다. 창의 `.task` 수명과 조회 작업 수명을 분리했습니다.

같은 사용자의 여러 앱 복사본은 `Application Support/AgentSwap/instance.lock`의 비차단 `flock`을 공유합니다. `AppDelegate`가 모든 화면의 엔진 시작 전에 `AppInstanceLock`을 확보하고 앱 종료까지 보유합니다. 잠금 파일은 사용자 소유의 일반 파일이며 0600 권한·심볼릭 링크 거부·exec 시 descriptor 종료 조건을 확인합니다. 두 번째 복사본은 설정과 인증을 읽거나 쓰는 엔진을 시작하지 않고 기존 앱을 활성화합니다. 실행 목록에서는 동일한 번들 ID `net.mercen.agentswap`의 로컬 개발 복사본도 확인합니다. 잠금 파일은 삭제하지 않으며 descriptor가 닫히면 커널이 소유권을 해제합니다. PID는 현재 잠금 소유자가 존재할 때만 제공하는 활성화 힌트입니다. 데모는 메모리 저장소만 사용하므로 별도로 실행할 수 있습니다.

`AccountIdentity`는 제공자·사용자 ID·워크스페이스 ID로 중복을 판단합니다. 재등록은 기존 UUID·별명·등록 순서·자동 전환 후보 설정을 보존하고 인증을 갱신합니다. `Credential`에는 비밀 값이 포함되므로 `PersistedState`에 넣지 않습니다.

목록 순서는 선택적 `accountDisplayOrder`에 계정 UUID만 저장합니다. 표시 시 중복·삭제된 UUID를 제외하고 새 계정을 등록 순서대로 뒤에 붙입니다. 제공자 필터·검색 중 이동은 보이는 계정이 차지하던 전체 목록의 위치만 교체합니다. 원래 `accounts` 배열은 등록 순서를 유지하므로 자동 전환 동률 기준과 조회 스케줄러 순서는 바뀌지 않습니다. 대시보드와 메뉴바는 같은 `displayAccounts`를 사용합니다.

계정별 재로그인은 공식 CLI의 격리 로그인을 사용하고, 반환된 제공자·사용자·워크스페이스가 선택한 계정과 정확히 같아야 합니다. 다른 계정의 결과로 새 계정을 추가하거나 기존 인증을 덮어쓰지 않습니다. UUID·별명·등록 시각·자동 전환 후보와 표시 순서를 유지합니다. 새 인증을 저장하기 전에 `requiresExplicitCredentialApplication`에 계정 UUID를 영구 저장하고, 저장·재읽기 확인 전에는 후속 조회를 하지 않습니다. 실패한 새 인증은 비공개 메모리에 보존해 저장을 재시도하며 정상 종료에서도 저장을 확인합니다. 이 표시가 남은 계정은 이전 네이티브 인증을 묵시적으로 vault에 채택하거나 새 인증을 자동 적용하지 않습니다. 적용과 표시 해제는 성공한 명시적 계정 전환 또는 명시적 현재 로그인 가져오기로 처리합니다.

적용 대기 중인 Claude 인증의 독립 갱신은 현재 CLI가 검증된 다른 계정일 때만 허용합니다. 제공자 잠금 안에서 실제 네이티브 세대를 다시 검사하고 같은 계정·미검증·확인 중 변경된 원본이면 OAuth 이전에 중단합니다. 이 경로는 갱신 응답을 vault에 먼저 보존하며 네이티브 인증에는 쓰지 않습니다. 만료된 적용 대기 인증의 수동 전환도 일반 갱신으로 이전 네이티브 grant를 채택하지 않습니다. Codex의 적용 대기 인증은 명시적으로 적용하기 전까지 자동 갱신을 보류합니다. 적용 대기인 현재 계정과 후보는 자동 전환에서 제외하며, 현재 계정의 새 인증을 먼저 적용하거나 현재 로그인을 명시적으로 선택하기 전에는 다른 계정으로 전환하지 않습니다.

Claude의 `oauthAccount`는 완전한 값이어도 토큰 소유자의 증명이 아닙니다. 처음 확인하는 토큰 쌍은 고정된 OAuth 프로필 API로 사용자·조직을 확인하며, 조회·갱신·전환 대상과 다르면 중단합니다. 성공한 계정 확인은 정확한 토큰 쌍의 지문과 함께 `Credential`의 선택적 binding으로 Keychain에만 저장합니다. 검증된 정확한 grant를 고정 OAuth 토큰 endpoint에서 갱신한 성공 응답은 같은 사용자·조직의 successor로 취급하고, 새 토큰 쌍으로 지문을 다시 계산해 **첫 영구 저장 전에** binding을 포함합니다. [OAuth 2.0의 같은 authorization grant 갱신 규칙](https://www.rfc-editor.org/rfc/rfc6749.html#section-6)에 근거하며, 캐시로 처음 보는 토큰의 소유자를 추측하는 경로는 아닙니다. 추가 프로필 요청의 제한·네트워크 실패가 새 토큰의 증명을 없애지 않습니다. 시작과 조회에서 검증된 binding을 어댑터의 제한된 메모리 캐시에 복원하므로 같은 토큰이 만료된 뒤 재시작해도 계정 캐시로 소유자를 추측하지 않습니다. 토큰·원본·계정·binding 버전이 다르면 이 증명을 사용하지 않습니다. 구버전의 미검증 토큰이 이미 만료됐다면 공식 클라이언트의 새 인증이나 독립 로그인이 필요할 수 있으며, 식별 불가는 저장소 확인 대기로 표시하고 캐시를 근거로 갱신하지 않습니다.

활성 Claude의 네이티브 프로필 요청이 HTTP 401이면 별도 오류로 구분합니다. 선택한 계정의 저장 인증에 정확한 binding이 있으면 그 인증으로 사용량만 조회할 수 있습니다. 이 경로는 활성 계정·보류된 세대를 유지하고, 만료 임박이나 사용량 401에도 토큰 갱신·네이티브 적용을 하지 않습니다. 사용량 실패 시 마지막 정상 값과 인증 상태를 보존하고 서버의 429 대기를 따릅니다. 저장 증명이 없거나 네이티브 읽기·형식·네트워크 오류가 발생하면 이 경로를 사용하지 않습니다.

같은 네이티브 access·refresh 토큰 쌍의 프로필 HTTP 401은 어댑터의 제한된 메모리 캐시에 60초 동안 보존해 다른 계정 조회가 같은 실패 요청을 반복하지 않게 합니다. 확인된 정확한 binding은 실패 캐시보다 우선하고, 외부에서 토큰 쌍이 바뀌면 즉시 새 프로필을 확인합니다. 실패 캐시는 소유자 증명으로 사용하지 않습니다.

## 동시성과 토큰 갱신

`AccountOperationQueue`의 비동기 잠금은 어댑터의 suspension point 전체를 감쌉니다. 제공자 단위 직렬화는 계정별 갱신뿐 아니라 제공자의 공유 인증 저장소 교체와 갱신 사이의 경쟁도 막습니다. 단순한 actor 격리만으로는 await 중 재진입을 막을 수 없으므로 별도의 대기열을 사용합니다.

회전된 토큰은 다음 사용량 요청 이전에 Keychain에 저장합니다. Codex의 조회와 수동 전환은 캐시된 활성 표시 대신 최신 네이티브 계정으로 갱신 소유권을 판단합니다. 실행 중인 Codex가 소유한 인증은 앱에서 갱신하지 않고 현재 인증을 다시 수집합니다. 네이티브 인증이 실제로 없지만 소비자가 실행 중인 경우에도 메모리의 grant 소유권을 증명할 수 없으므로 직접 갱신하지 않습니다. 비활성 계정은 필요할 때 직접 갱신합니다. 실행 중인 소비자의 사용량 조회가 401이면 네이티브 successor를 다시 수집해 한 번 재조회하고, 아직 갱신되지 않았다면 인증 상태와 마지막 정상 응답을 보존합니다. HTTP 403은 권한 오류로 구분해 토큰 갱신을 유발하지 않으며, 서버의 429와 일시적 네트워크 오류도 마지막 정상 응답을 보존합니다.

검증된 갱신 응답은 첫 영구 저장이 확인될 때까지 private actor 또는 `@ObservationIgnored` 엔진 메모리에 보존합니다. 다음 OAuth 요청·네이티브 재수집·전환 전에 저장을 재시도합니다. 활성 Claude의 재시도는 정확한 복구 marker만 저장하고 네이티브 인증을 적용하지 않습니다. 비활성 Claude는 vault 저장을 확인한 뒤 계정 UUID와 이전/새 인증의 SHA-256 지문을 엔진에 전달합니다. 엔진은 기존 비밀 정보가 없는 predecessor 상태를 먼저 저장하며 연속 갱신에서는 최초 predecessor를 유지합니다. 이 정보로 재시작 후 오래된 네이티브 인증이 새 vault 인증을 덮어쓰지 않게 합니다. Claude의 같은 계정·같은 토큰은 설치 CLI를 위한 JSON 표현과 공유 필드가 다를 수 있으므로 알려진 형식을 파싱해 같은 grant인지 확인합니다. 네이티브 쓰기 직전의 바이트 일치 조건은 유지합니다.

`AppDelegate`는 정상 종료에서 `.terminateLater`로 응답합니다. 엔진이 새 작업을 막고 스케줄러·로그인·초기화·제공자 대기열의 기존 작업을 기다린 뒤 새 인증과 복구 상태를 비상호작용으로 저장합니다. 저장을 확인하지 못하면 종료를 거절하고 조회를 재개합니다. 첫 영구 사본이 없는 동안의 강제 종료·시스템 중단이나 서버 응답을 받기 전 연결 단절까지 복구한다고 보장하지 않습니다.

네이티브 저장소 적용을 기다리는 갱신 인증은 이전 원본의 비밀 정보가 없는 SHA-256 지문을 상태에 기록합니다. 오래된 네이티브 인증을 재수집해도 새 Keychain 인증을 덮어쓰지 않으며, 외부에서 다른 인증으로 바뀌었다면 묵시적으로 선택하지 않고 재확인을 요구합니다.

Claude의 불완전한 계정 캐시는 확인된 계정 정보와 동일한 인증 세대를 함께 확인할 때 보완합니다. 이미 있는 사용자·조직 ID가 충돌하거나 형식이 잘못되면 토큰 갱신과 복구를 중단합니다. 회전된 새 토큰을 앱 Keychain에 저장하지 못해도 복구 자료를 보존하고 명시적 복구 전에는 계정 전환을 허용하지 않습니다. 활성 인증 갱신은 HTTP 요청으로 기존 갱신 토큰을 소비하기 전에 네이티브 저장 가능한 입력 크기를 검증합니다. OAuth 갱신은 기록된 scope를 유지하며, 기본 클라이언트에 scope가 없으면 설치된 CLI의 기본 권한을 사용합니다. 여기에는 플러그인 권한이 포함됩니다. 별도 클라이언트의 권한을 알 수 없으면 추측해 갱신하지 않습니다.

인증된 Claude 프로필과 네이티브 원문이 정확히 같다면 오래된 정상 형식의 계정 캐시와 무관하게 실제 소유자의 갱신을 진행할 수 있습니다. 이 경로는 캐시를 수정하지 않으며, 원래 설정 파일의 정확한 바이트와 부재를 새 회전 marker에 기록합니다. 갱신 전·적용 직전·실패 복구에서 설정과 원문 세대를 다시 확인하며 변경됐으면 새 인증을 보존하고 적용을 중단합니다. 이 선택적 기록이 없는 이전 marker는 기존 계정 캐시 검증을 계속 사용합니다.

## 저장소 트랜잭션

앱에 저장하는 계정 인증은 Keychain 서비스 `net.mercen.agentswap`을 사용합니다. 전환 복구 저널과 Claude 토큰 회전 복구 자료는 `net.mercen.agentswap.recovery`에 저장합니다. 계정 인증의 항목 이름은 계정 UUID이며, 메타데이터·설정·조회 캐시는 Application Support의 `state.json`에 저장합니다.

제공자 저장소 변경은 동기 경계에서 잠금·읽기·검증·백업·변경·검증을 처리합니다. 파일은 원자적 교체와 0600 권한을 사용합니다. Claude OAuth와 계정 메타데이터처럼 여러 위치를 변경할 경우 복구 저널을 앱 Keychain에 먼저 저장합니다. 일부 단계가 실패하면 원본을 복원하며 중단된 저널도 복구할 수 있습니다.

완료를 기록한 인증 저널은 이후 공식 CLI가 토큰을 갱신하거나 다른 계정으로 바꿔도 롤백하지 않습니다. 저널 형식과 허용 위치를 검증한 뒤 앱의 완료 저널만 정리합니다. 미완료 저널은 계속 현재 바이트가 before/after 중 하나인지 확인하며 제3의 인증 세대에서는 복원을 보류합니다. Claude 회전 복구 자료에는 공유 MCP·플러그인 필드까지 반영한 정확한 네이티브 after 이미지를 저장하고 다시 계산해 검증합니다.

Claude 회전 marker가 남은 동안 같은 계정의 공식 CLI가 제3 세대로 갱신한 경우, 활성 계정 상세의 명시적 `현재 로그인 유지하고 복구` 경로를 사용합니다. 완료된 전환 저널은 알려진 형식·위치를 검증하고 정확한 원문을 재확인한 뒤 private 기록만 정리합니다. 미완료 저널은 네이티브 Keychain·인증 파일의 before/after가 회전 marker의 원본·대상과 정확히 같은 경우에만 함께 보관합니다. 설정 변경이나 알 수 없는 세대의 저널, 계정·조직 불일치, 네이티브 Keychain·파일 충돌, 알 수 없는 vault 세대에서는 중단합니다. 현재 인증으로 프로필 API를 다시 확인하며 HTTP 요청 중 제공자 잠금을 해제하고, 잠금을 다시 얻은 뒤 marker·저널·네이티브·설정·vault의 정확한 원본을 재확인합니다. 네이티브 인증과 설정에는 쓰지 않습니다.

이 복구는 기존 marker·일치하는 미완료 저널과 필요한 vault 자료를 recovery Keychain에 보관하고 읽기를 검증한 뒤 현재 인증을 앱 vault에 저장·검증하고 저널과 활성 marker를 차례로 제거합니다. 네이티브와 설정의 보관 기록에는 원문 대신 SHA-256 지문을 둡니다. 실패 후 재시도는 같은 기록을 사용하며 프로필 표시명 변화가 동일한 인증의 재시도를 막지 않습니다. 계정별 보관 목록을 먼저 저장해 계정 삭제 시 해당 보관 인증도 정리합니다. 미완료 복구가 있으면 삭제를 보류합니다. 복구 후 저장소 오류의 재시도 대기만 해제하며 API의 `retryAfter`는 유지합니다.

## Claude 네이티브 Keychain 전송

기존 Swift SDK 저장 경로의 실제 Claude 전환에서는 앱의 저장 후 읽기와 API 조회가 성공해도 공식 CLI가 같은 인증을 읽지 못했습니다. SDK의 비밀 값 갱신과 보호된 partition 접근 권한 변경을 조사했고, 원래 권한을 `SecItemSetAccess`로 정확히 복원하는 방식은 데이터베이스 암호 없이 거부됐습니다. OS 암호를 수집하는 우회는 추가하지 않습니다.

기본 `ClaudeKeychainAccess`는 Claude 네이티브 구독 인증에만 Apple 도구의 읽기·쓰기를 사용합니다. 작은 인증은 Apple `/usr/bin/security`로 씁니다. 인자는 고정된 `-i`, `-q`이며 명령과 소문자 hex 비밀 값은 stdin 파이프로 전달합니다. 원래 자료와 복원 자료를 포함한 각 명령은 LF를 제외하고 최대 4094바이트로 제한합니다. 같은 자식 프로세스에서 쓰기 뒤 읽기를 수행하고 정확한 바이트를 확인한 다음 Swift 트랜잭션도 결과를 재확인합니다. 읽기 출력의 hex 표현은 원래 바이트로 복원하며 stderr·항목 메타데이터는 사용자 메시지나 로그로 내보내지 않습니다. `Claude Code` API-key 항목은 호환성 확인용 읽기만 허용하고 쓰기·삭제를 거부합니다. 앱 vault·복구·Codex 항목은 이 도구에 넘기지 않고 기존 Swift 저장소에 위임합니다.

명령 길이를 초과하는 인증은 Apple 서명을 검증한 `swift-frontend`가 번들 `ClaudeKeychainWriter.swift`를 실행해 저장합니다. 인증은 JSON-base64 표준 입력으로만 전달하며, 코드·인자·환경 변수·모듈 캐시에 포함하지 않습니다. 기존 항목은 하나의 legacy 참조와 소유 Keychain을 확인하고 값만 갱신합니다. 없는 항목은 `/usr/bin/security`만 신뢰하는 ACL로 한 번에 생성하며 중간 seed를 쓰지 않습니다. helper 자체 읽기는 권한이 다를 수 있으므로 성공 근거로 사용하지 않고, 별도 SecurityTool이 같은 바이트를 읽어야 성공합니다. interpreter의 Apple 서명·식별자, SDK·resource 및 컴파일된 resource digest를 쓰기 전에 확인합니다. Apple Command Line Tools 또는 Xcode가 없으면 큰 원본의 복원 가능성을 보장하지 못하므로 전환을 중단합니다.

트랜잭션은 저널이나 네이티브 쓰기를 시작하기 전에 모든 before/after 자료를 검증합니다. 복구도 모든 이전 자료를 먼저 검증하며, 사전 검사 뒤 각 복원 쓰기 직전에 현재 세대가 해당 mutation의 정확한 before 또는 after인지 재확인합니다. 검사 도중 외부에서 만들어진 제3 인증이나 로그아웃을 이전 백업으로 덮어쓰지 않습니다. 인증 전송의 추가 안전 상한은 1 MiB이며, 실제 지원 크기는 설치 Claude CLI의 동기 SecurityTool 읽기 `maxBuffer: 1e6`을 따릅니다. 출력 가능한 ASCII는 원본 길이+LF, 다른 바이트가 있으면 hex 길이(원본의 2배)+LF를 계산해 1,000,000바이트 이내인지 대상·복원 자료 모두 검사합니다. 따라서 ASCII는 999,999바이트, 비출력 바이트가 있는 기존 자료는 499,999바이트까지 지원합니다. 초과하면 원본을 변경하지 않고 거부합니다. 인증 JSON의 Unicode와 제어 문자는 ASCII escape로 표현하되 JSON의 의미와 MCP·플러그인 자료를 유지합니다.

SecurityTool의 네이티브 백그라운드 접근은 기본 Keychain 잠금을 먼저 확인하고 2초, 직접 사용자 동작은 120초로 제한합니다. 큰 인증 helper는 자식 프로세스에서 직접 `SecKeychainSetUserInteractionAllowed`를 설정합니다. 백그라운드는 UI를 금지하고 첫 SDK 컴파일을 포함해 30초, 사용자 동작은 120초이며 외부 SecurityTool 재읽기는 기존 제한을 유지합니다. 시스템 모듈 캐시는 사용자 소유의 0700 디렉터리에 저장하고 인증을 넣지 않습니다. 취소·시간 초과 시 자식에 TERM을 요청하고 필요한 경우 KILL로 종료하며 종료와 출력 배출도 제한합니다. SecurityTool에는 공개적인 승인 UI 금지 옵션이 없어 백그라운드에서 창이 절대 나타나지 않는다고 보장하지 않습니다. 취소 후 저널 복구만 TaskLocal로 취소 차단을 해제하고 동일한 권한·시간 제한을 유지합니다.

합성 항목의 외부 CLI 읽기와 최신 앱의 실제 Claude CLI A → B → A가 통과했습니다. 각 전환 후 공식 CLI의 로그인·사용자·워크스페이스 일치와 API 조회를 확인했고 공유 설정도 유지됐습니다. 네이티브 인증 쓰기 뒤 별도의 Claude 항목 승인은 필요하지 않았습니다. 이 증거는 설치된 버전과 지원 입력 길이 안의 실제 자료에 한정합니다. 이 CLI 검증 자체는 데스크톱 로그인 변경과 기존 Code 대화의 다른 계정 재개를 입증하지 않습니다. Desktop 2.42304.0의 별도 결합 전환 검증은 검증 기록에 구분해 남깁니다.

## 전환 상태와 브라우저 로그인

전환 가드는 현재 계정·실행 중 작업·저장 오류·시작 및 종료 상태·계정 인증·제공자 저장소의 쓰기 호환성을 함께 확인합니다. UI는 같은 가드로 이유를 표시합니다. 현재 A의 원본을 복원할 수 없으면 B로의 전환도 보류합니다. 조회 완료와 로그인 완료 후 호환성을 다시 검사하며, 사용자의 명시적 재확인은 제공자 대기열 안에서 저장소 접근만 검사합니다. 저장된 인증 접근 허용은 기존대로 선택한 vault 항목의 읽기만 수행합니다.

Claude CLI는 자동 localhost 콜백 URL을 열면서 다른 수동 코드 URL을 fallback으로 출력합니다. 앱은 출력 URL을 자동으로 열지 않습니다. 검증한 링크 하나를 로그인 runner의 메모리에만 보관하고 사용자가 요청한 재열기에서만 브라우저를 엽니다. 종료·취소 시 링크와 UI 모니터를 정리하며, 늦게 끝난 이전 세대의 열기 결과가 새 로그인에 영향을 주지 않게 합니다. `코드#state` 표준 입력 제출은 유지합니다.

## 조회와 서버 제한

서버의 HTTP 429 대기는 계정별 `UsageCache`와 함께 `PersistedState.providerRetryAfter`에도 기록합니다. 제한 범위가 계정별인지 확인할 수 없으므로 같은 제공자의 후속 조회·갱신과 계정 전환을 함께 보류합니다. 다른 제공자는 계속 조회합니다. 대기열을 얻은 뒤에도 다시 검사하므로 동시에 요청한 전체 새로고침이 제한을 우회하지 않습니다. 시작 시 기존 캐시의 명시적인 `serverRateLimit` 중 가장 늦은 시각을 복원하고 네이티브 프로필 요청도 보류합니다. 새로고침·접근 승인·재시작이나 다른 계정의 성공으로 서버 대기를 지우지 않으며, 마지막 정상 값과 인증 상태를 유지합니다. 목록·상세·메뉴바에는 서버 조회 제한과 시스템 시간대의 재시도 시각을 표시합니다.

## 자동 전환

순수 함수 `AutomaticSwitchPolicy.decide`가 실행 여부·유예·현재 한도·후보 선택을 결정합니다. 후보는 사용자가 체크했고 정상 인증이며 반환된 모든 공통 한도의 사용률을 알고 있어야 합니다. 플랜마다 공통 창의 개수와 길이가 달라도 각 계정의 최소 잔여율로 비교합니다. 만료된 초기화 시각, 오류, 최대 보존 기간을 넘긴 스냅샷도 제외합니다.

후보의 공통 창에서 가장 낮은 잔여율을 점수로 사용합니다. 점수가 같으면 등록 순서를 따릅니다. 모델별 한도는 정보 표시용이며 v1의 자동 전환 결정에 사용하지 않습니다. 적용 성공에만 활성 계정과 마지막 전환 시각을 변경합니다. 재실행 대기는 별도 상태로 표시합니다.

Codex의 코드 검토 한도는 구독 공통 한도와 구분해 추가 한도로 표시합니다. 이 값은 자동 전환의 임계치와 후보 점수에 포함하지 않습니다.

## 데스크톱 프로세스 경계

데스크톱은 번들 ID로 찾습니다. 실행 중인 인증 소비자를 검사한 뒤 수동 재실행을 요청한 경우에만 정상 종료를 요청합니다. 별도의 CLI·IDE를 강제로 종료하지 않습니다. 종료 후 다시 검사하고 최신 원본을 앱 Keychain에 저장한 뒤 대상 인증을 적용합니다. 실행 중인 프로세스가 하나라도 남으면 쓰기를 보류합니다.

Codex의 대상 인증이 종료 전 현재 인증과 정확히 같은 경우에는 종료 후 마지막으로 수집한 세대를 대상에 사용합니다. 같은 계정의 별도 vault successor와 다른 계정의 대상은 그대로 유지합니다. 백업 콜백은 등록된 계정에 최신 인증을 저장해야 성공하며, 등록되지 않은 원본에서는 전환을 보류합니다. 이 작업이 정상 종료를 확인했지만 인증 적용에 이르지 못했다면 호환성과 reliable 프로세스 조회가 성공할 때만 기존 데스크톱을 다시 엽니다. 종료 거부·미확인이나 복구 대기에서는 재실행하지 않습니다.

## 독립 Claude Desktop 로그인 프로필

`AppModel.claudeDesktopProfiles`의 `ClaudeDesktopProfileModel`은 대시보드와 메뉴바가 공유합니다. CLI와 독립적인 Desktop 로그인은 계정별로 공식 Desktop에 직접 로그인해 유지합니다. `ClaudeDesktopProfiles/profiles.json`에는 이름과 UUID만 저장하며, 이 프로필 기능은 Desktop 쿠키·암호화 키·OAuth 자료를 수집하거나 복사하지 않습니다. 실제 로그인·갱신·대화 저장은 각 UUID의 데이터 폴더를 사용하는 공식 Desktop이 담당합니다. 아래의 2.42304.0 로그인 스냅샷 결합 전환과 별개입니다.

프로필 열기는 CLI·명시적 Desktop 결합 전환과 같은 `.claude` 작업 대기열을 사용합니다. 기존 Desktop 실행도 포함해 과거 대화 보존 저널의 경로 안전성·부재와 Desktop Keychain 복구 기록을 먼저 검사하고 실행 직전 다시 확인합니다. 미완료·알 수 없는 기록에서는 프로세스 조회·종료·실행을 시작하지 않습니다. 설치·프로세스 상태를 확인한 뒤 정상 종료를 요청하고 PID·시작 시각으로 추적한 모든 관련 프로세스가 사라질 때까지 기다립니다. 마지막 경로·프로세스 재확인 후 `--user-data-dir` 인자로 선택한 private 폴더를 전달합니다. 강제 종료·전체 데이터 폴더 교체·쿠키 DB 편집은 하지 않습니다. 원래 Desktop은 인자 없는 기본 실행으로 다시 엽니다. 열린 프로필 receipt는 로그인 계정 검증이나 인증 유효성을 뜻하지 않습니다.

설치된 Desktop 3.1623.0의 `index.pre.js`와 주 진입 chunk에서 확인한 Electron 데이터 폴더·로그인 경로를 사용하며 새 프로필 실행을 이 버전으로 제한합니다. 패키징된 앱이 `CLAUDE_USER_DATA_DIR`를 제거하므로 이 환경 변수에 의존하지 않습니다. 데이터 폴더 변경은 Claude in Chrome의 로컬 pairing을 제한하며, Code 탭의 토큰 broker는 `app.getPath("userData")` 아래 프로필별 자료를 사용합니다. 일부 CLI 설정·transcript는 공용 `~/.claude`를 사용할 수 있으므로 전체 파일 격리를 보장하지 않습니다. 브라우저 로그인 콜백·실계정 Code 요청·기존 대화의 계정 간 이어쓰기는 fixture로 입증하지 않습니다.

종료 진입은 프로필 작업의 신규 진입을 먼저 차단한 뒤 CLI 로그인 취소·스케줄러 종료를 처리하고 프로필 작업을 기다립니다. 프로필 작업이 CLI 로그인 소유 대기열을 기다리는 상태에서도 종료가 교착되지 않게 합니다. 인증 저장 실패로 앱 종료가 보류되면 프로필 작업 진입도 복원합니다.

## Claude Code 대화와 인증의 분리

일반·자동 Claude 전환은 인증만 변경합니다. 비공개 Desktop 대화 목록의 형식·버전·크기·경로와 `.claude/projects`의 존재 여부를 검사하지 않고, 목록·transcript를 읽거나 쓰거나 복사하지 않습니다. Claude Desktop 프로세스도 조회·종료·재실행하지 않습니다. 인증과 `oauthAccount`의 교체, 최신 원본 백업, 대상 토큰 갱신의 영구 저장, 원본 계정·정확한 인증 세대 재확인은 기존 제공자 트랜잭션에서 유지합니다.

계정 전환 전, 인증 적용 직전, 원본 백업 콜백에서는 AgentSwap 자체의 복구 기록만 검사합니다. 이전 버전의 `claude-session-preservation/pending.json`은 상위 상태 경로의 소유권·권한·링크 안전성을 확인하고 정확한 파일의 `lstat` 결과가 `ENOENT`일 때만 통과합니다. 이 파일은 존재만으로 차단하며 내용을 대화 형식으로 해석하지 않습니다. 새 Desktop 전환의 Keychain 저널도 별도로 확인하며, 함께 전환을 소유한 정확한 준비 ID만 준비 단계의 CLI 적용을 통과합니다. 시작 시 원본 인증을 읽지 못한 것은 로그아웃의 증거가 아닙니다. 원본이 없다는 경로는 제공자 어댑터와 잠금 아래의 저장소가 실제 부재를 각각 재확인해야만 인증을 적용합니다.

이전 대화 보존 저널이 남으면 일반 전환은 보류하고 별도의 명시적 복구를 제공합니다. 실제 현재 CLI 계정을 원본과 대상으로 동일하게 전달해 기존 복구만 수행하며 새 대화 목록을 준비하지 않습니다. Desktop이 실행 중이면 직접 정상 종료한 뒤 복구를 재시도하도록 안내합니다. 알 수 없는 저널·버전·외부 변경은 기존 복구 조건대로 보존하고 중단합니다. 이전 보존 구현은 이 복구 및 합성 fixture의 호환성 경계로 남으며 새 계정 전환에는 연결하지 않습니다.

대화 재개는 계정 상세의 별도 안내에서 공식 `claude --resume` 및 Desktop `/resume` 흐름으로 연결합니다. 대화 원본을 유지하는 것과 다른 계정의 Desktop 목록에 같은 대화가 나타나는 것은 구분합니다. Claude Desktop 로그인은 CLI 로그인과 별개이며, 계정 간 Desktop 대화의 자동 이전·실행 재개나 원격 연결 이전을 보장하지 않습니다. 공식 재개는 [세션 문서](https://code.claude.com/docs/en/sessions)와 [Desktop 안내](https://code.claude.com/docs/en/desktop#coming-from-the-cli)를 따릅니다.

## 명시적인 Claude Desktop 함께 전환

계정 상세의 `Desktop과 CLI 함께 전환`은 일반·자동 전환과 분리된 수동 작업입니다. 처음에는 각 계정으로 공식 Desktop 로그인을 완료하고 `이 계정의 Desktop 로그인 저장`으로 등록합니다. Desktop의 실제 사용자 UUID를 등록 계정과 대조하며 CLI 토큰을 Desktop 로그인으로 재사용하지 않습니다. Desktop과 CLI가 이미 서로 다른 계정인 경우도 허용합니다.

내부 저장 형식에 의존하므로 현재 결합 전환 지원 버전은 Desktop `2.42304.0`으로 제한합니다. 로그인 스냅샷에 Desktop 버전을 저장하며 다른 버전에서 캡처한 인증을 적용하지 않습니다. 일반 CLI 전환에는 이 Desktop 버전 제한을 적용하지 않습니다.

Desktop 인증 스냅샷은 `net.mercen.agentswap.desktop` Keychain에 계정 UUID별로 저장합니다. 네이티브 `config.json`의 확인된 로그인 키와 Cookies·Local Storage·Session Storage·IndexedDB의 불투명 파일 자료만 대상입니다. 앱 상태 JSON이나 평문 백업에는 넣지 않습니다. 계정 외 설정과 MCP·플러그인 설정은 보존합니다. 새 인증 키·알 수 없는 저장 형식, 링크·소유권·크기 한도 위반은 쓰기 전에 중단합니다.

`lastKnownAccountUuid`는 등록 계정 후보를 찾는 캐시이며 로그인 증명으로 사용하지 않습니다. 저장 전에는 `Claude Safe Storage`의 키를 읽기 전용으로 사용해 두 OAuth 캐시의 알려진 `v10` 형식을 메모리에서만 복호화합니다. 독립적으로 사용할 수 있는 V1은 정확히 빈 JSON 객체인 경우만 허용합니다. V2의 모든 활성 항목이 같은 사용자·조직을 가리켜야 하며, 만료 시각이 가장 늦은 토큰 하나를 선택해 고정된 Anthropic OAuth 프로필 API의 사용자·조직 UUID를 대조합니다. 서로 다른 토큰의 만료 시각이 같으면 선택하지 않습니다. 인증 갱신이나 Safe Storage 쓰기는 하지 않습니다. 이 절차를 통과한 두 암호화 캐시와 식별자의 지문을 스냅샷 v2에 묶고, 확인 중 변경된 파일·프로세스는 다시 검사합니다. 프로필 확인이 없는 이전 스냅샷은 다시 저장해야 합니다.

복호화 호환성은 [Electron 44.7.2 safeStorage 구현](https://raw.githubusercontent.com/electron/electron/v44.7.2/shell/browser/api/electron_api_safe_storage.cc)과 [Chromium의 legacy v10 구현](https://chromium.googlesource.com/chromium/src/+/93d0dcd55046ac06154f4d642c26d7697c4b0304/components/os_crypt/sync/os_crypt_mac.mm)에 한정합니다. `v11` 등 알 수 없는 암호문이나 계정·프로필 불일치는 저장을 거부합니다. 실제 API 확인이 실패하면 캐시 UUID만으로 계속 진행하지 않습니다.

수동 함께 전환은 대상 백업을 검증하고 Desktop을 정상 종료한 뒤, 완전히 종료된 원본을 다시 수집해 Keychain 백업과 복구 기록의 저장을 확인합니다. 기존 CLI 전환의 대기열·원본 백업·정확한 세대 검사 아래 CLI를 적용한 다음 Desktop 로그인과 Code 목록을 적용하고 다시 엽니다. 종료를 확인하지 못하면 인증을 쓰지 않으며 강제 종료하지 않습니다. 이미 확인한 하위 프로세스가 고아가 되어도 같은 PID·시작 시각이면 다음 재시도에서 관련 프로세스로 유지하고 새 자식까지 추적합니다. 종료와 PID 재사용은 추적에서 제거하며, 조회가 모호하면 계속 보류합니다. 좀비는 BSD 상태 또는 성공·정확한 크기의 `KERN_PROC_PID` 결과가 `SZOMB`일 때만 종료로 인정합니다. libproc의 `ESRCH`만으로는 접근 은폐와 구분할 수 없어 이 오류 쌍을 종료 증명으로 사용하지 않습니다. 별도의 `kill(pid, 0)`이 `ESRCH`로 실패한 경우는 프로세스 부재로 인정합니다.

Code 목록은 등록된 원본·대상 사용자와 조직의 버킷만 다룹니다. 연결에 필요한 최소 식별자와 시각만 검사하고 알 수 없는 필드를 허용합니다. 새로 추가되는 목록은 원계정의 `bridgeSessionIds` 연결 이력을 제외하고 복사하며, 이력이 없는 자료는 원문 바이트를 유지합니다. 같은 대화의 최신 목록을 반영할 때 대상의 제목·보관·별표와 대상 소유의 `bridgeSessionIds` 값·순서·필드 부재를 유지합니다. 삭제 표시와 ID 충돌을 확인하고, 공유 transcript는 복사하거나 수정하지 않습니다. 이미 실행 중인 원격 연결은 이전하지 않습니다. 연결 해제 후 남는 `bridgeSessionIds`는 계정별 cloud-to-local 매칭·재부착·정리에 쓰이므로 다른 계정으로 전달하거나 합치지 않습니다. 양쪽 이력의 배열 형식을 검증하고, 변환 후에도 파일별 크기 한도를 확인합니다. 목록과 연결된 transcript의 지문은 인증 적용 전후와 복구에서 재확인합니다.

CLI와 Desktop은 하나의 원자 트랜잭션이 아닙니다. CLI 성공 뒤 Desktop이 실패하면 CLI를 이전 인증으로 되돌리지 않고 부분 성공을 표시합니다. 복구 자료는 `net.mercen.agentswap.recovery` Keychain에 남기며 정확한 원본·대상 상태에서만 복구합니다. 제3의 로그인이나 외부 파일 변경을 덮어쓰지 않습니다. 중단된 Desktop 기록이 있으면 일반 CLI 전환도 보류하고 명시적인 Desktop 복구를 안내합니다. 완료 기록 정리는 이후 Desktop 로그인·토큰 갱신을 롤백하지 않습니다.

이 기능은 Desktop의 비공개 로컬 저장 방식에 의존합니다. 일반 Chat·Cowork·클라우드 세션의 계정 간 이전은 포함하지 않습니다. 실제 Desktop 로그인 변경, 기존 Code 대화 표시, 새 응답으로 이어쓰기의 증거는 각각 따로 기록합니다.

전환 결과는 대시보드 전체의 고정 40pt 상태바에 표시하고, 전체 메시지는 440×240pt 팝오버에서 읽고 선택할 수 있습니다. 로컬 Code 형식 오류 이후의 별도 CLI 전환 확인창은 더 이상 사용하지 않습니다.

## GitHub Releases 업데이트

앱 타깃은 Sparkle 2.10.0의 표준 업데이트 UI를 사용합니다. 시작 시와 수동 확인 시, 정기 확인 직전에 GitHub Releases 목록을 읽고 공개된 유효 SemVer 중 가장 높은 버전을 선택합니다. 설치본이 베타이면 prerelease도 허용하고 정식 버전이면 정식 릴리스만 허용합니다. draft 또는 해당 태그의 `appcast.xml`과 정확한 Universal ZIP이 모두 준비되지 않은 릴리스는 선택하지 않습니다. 피드와 ZIP은 공개 GitHub Release 첨부 파일에 한정하며 별도 피드 서버를 사용하지 않습니다.

자동 확인은 기본 24시간 간격이고 자동 다운로드·설치는 기본 꺼짐입니다. 업데이트 설치·재실행은 Sparkle의 사용자 흐름을 사용하며 기존 `AppDelegate`의 `.terminateLater` 저장 대기를 유지합니다. 데모 모드에서는 updater와 네트워크 확인을 시작하지 않습니다.

업데이트 ZIP은 EdDSA 서명을 필수로 하며 공개키만 앱 번들·저장소에 포함합니다. 비밀키는 로컬 Keychain 또는 CI 비밀 저장소에서 서명 도구로 전달하고 빌드 산출물·명령 인자·로그·Git에 기록하지 않습니다. Sparkle이 압축 해제·설치 전에 서명을 확인합니다. beta.8부터 앱의 서명은 공개 DER로 고정한 전용 인증서를 사용하며 DR이 앱 식별자와 인증서를 함께 요구합니다. 인증서가 없거나 다르면 공개 패키징을 중단합니다. 이 서명은 Developer ID 서명이나 Apple 공증이 아닙니다. Keychain의 일반 ACL과 별개인 partition 검사는 self-signed 앱을 `cdhash:`로 구분하므로, 고정 DR만으로 업데이트 간 접근을 유지하지 못합니다. 기존 항목은 새 바이너리의 전경 읽기 승인이 필요할 수 있으며, 쓰기만으로 승인 창이 열린다고 가정하지 않습니다. 접근 유지의 완료 조건에는 실제 배포 바이너리 두 버전 사이에서 읽기와 갱신 저장까지 모두 포함합니다.

## 업데이트 사이의 앱 Keychain 식별 유지

개발 중인 `AppVaultKeychainAccess`는 앱 vault·복구·Desktop 스냅샷의 세 서비스만 고정 XPC 구성 요소로 보냅니다. 제공자의 네이티브 저장소는 기존 호환성 경계를 사용합니다. 서비스·항목 형식을 모르면 중단하며 직접 SDK 호출로 대체하지 않습니다. 이 구성 요소의 배포 pin이 없는 소스 빌드는 인증 접근을 거부합니다. 설치된 beta.12에 이 경로가 적용됐다는 뜻은 아닙니다.

`AgentSwapVaultService.xpc`는 검토한 소스 커밋으로 CI에서 한 번 Universal 빌드·서명하고, 공개 manifest에 소스·실행 파일 SHA-256·아키텍처별 cdhash·전체 파일 목록을 기록합니다. 앱 패키징은 검증한 같은 바이트만 복사하며 재빌드·재서명하지 않습니다. 앱은 고정 인증서·서비스 ID·cdhash와 실행 파일 digest를 확인합니다. 서비스는 같은 인증서와 앱 ID의 호출자 및 같은 사용자만 허용합니다. 공유 Apple 인터프리터에 앱의 저장 인증을 맡기거나 ACL을 임의로 넓히지 않습니다.

이름으로 찾는 XPC 연결은 익명 endpoint만 반환하며 인증 값을 전달하지 않습니다. 인증 RPC는 그 프로세스의 익명 endpoint에 연결한 뒤 같은 연결에서 검증된 nonce·프로토콜 버전·UID 응답을 받아야 시작합니다. 구성 요소가 종료되면 endpoint도 무효가 되므로 이름 재연결로 교체된 프로세스에 인증을 보내지 않습니다. 취소와 요청 기한은 credential 전송 직전과 응답 수신 뒤에 다시 확인합니다.

서비스의 `XPCService.JoinExistingSession`은 반드시 `true`입니다. 같은 UID·서명만으로 호출 앱의 사용자 보안 세션을 공유하지 않으므로, 번들 검증과 서명된 IPC fixture에서 이 조건을 따로 확인합니다. helper가 독립 Keychain을 직접 unlock한 결과만으로 사용자 로그인 Keychain 접근을 입증하지 않습니다.

SDK 접근과 프로세스 전역 승인 UI 정책은 하나의 동기 잠금 안에서 처리합니다. 기존 항목은 정확한 항목 참조와 소유 Keychain을 고정해 먼저 읽고, 쓰기 직전 연결 상태를 다시 확인합니다. 쓰기 성공은 정확한 SDK readback과 IPC 응답 바이트의 일치를 모두 요구합니다. 연결 종료·기한 만료로 실제 SDK 쓰기의 완료 여부가 불명확하면 기존 successor·복구 보존 경계를 따르며 OAuth 요청을 다시 교환하지 않습니다. 기존 복구 자료를 잘라 넣거나 새 크기 제한으로 우회하지 않습니다.

이전 앱이 만든 항목은 새 서비스의 첫 접근에 사용자의 명시적 승인이 필요할 수 있습니다. 같은 서비스 바이트를 재사용하는 동안의 업데이트 연속성과 이 최초 이행은 별도 검증 대상입니다. 보안 수정으로 서비스 자체를 교체할 때도 새 식별값과 승인 이행을 계획해야 합니다. 현재 일반 계정 조회 복구, 합성 XPC 검증, 공개 패키징, 설치 앱의 실제 이행·조회는 각각 [검증 문서](VALIDATION.md)에 구분합니다.

## v1 범위

기본 로컬 프로필의 구독 계정과 개인·팀 `.app` 제공에 집중합니다. API 키, 계정별 프로젝트 실행, 인증 내보내기, 클라우드 동기화는 제외합니다. 배포용 서명·공증·DMG는 배포 인증서가 준비된 뒤 적용합니다. 실제 로그인·사용량 검증 결과는 `VALIDATION.md`에 별도로 기록합니다.
